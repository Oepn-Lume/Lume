# 为什么 Gemma4 还不能替代云端协作
## 一次对 `Lume Treasury` 全量 Session 历史的系统对比

过去我们在讨论本地模型时，常常会默认一个前提：只要模型参数够大、本地推理够快、再加上一些微调数据，它迟早能逼近云端模型的表现。但当我们真的把本地模型放进真实工作流里，并用完整历史 session 去回放时，事情就没有这么简单了。

这次在 `Lume Treasury` 里，我们做了一件非常具体的事：把 `.codex/sessions` 和 `archived_sessions` 中保留下来的全部历史会话都拉出来，把其中所有可比较的云端回复重新交给本地 `gemma4:31b` 跑一遍，然后逐条对照云端原始输出，看看它到底差在哪里。

这不是一次“抽样体验”，也不是几条示例 prompt 的印象式判断，而是一轮覆盖完整保留历史的全量对比。最后生成的结果在 [gemma_vs_cloud_all_sessions.md](/Users/yh-PC-003/Desktop/codex/lume/data/reports/gemma_vs_cloud_all_sessions.md)、[gemma_vs_cloud_all_sessions.json](/Users/yh-PC-003/Desktop/codex/lume/data/reports/gemma_vs_cloud_all_sessions.json) 和 [gemma_vs_cloud_all_sessions_supplemental_events.jsonl](/Users/yh-PC-003/Desktop/codex/lume/data/reports/gemma_vs_cloud_all_sessions_supplemental_events.jsonl)。对比脚本本身在 [compare_gemma_vs_cloud_sessions.py](/Users/yh-PC-003/Desktop/codex/lume/scripts/compare_gemma_vs_cloud_sessions.py)。

这轮对比让我们更清楚地看到了一个核心事实：

**Gemma4 现在最大的差距，不是“不会回答”，而是“不会像云端那样延续现场状态”。**

## 一、为什么要做这次全量对比

`Lume Treasury` 的目标，从来不是单纯做一个本地聊天壳子。它真正想做的是，把每一次云端智能消费，逐步沉淀为本地能力资产。换句话说，我们不是为了“本地也能聊两句”，而是为了构建一个真正能接管部分任务的 `Battery Model`。

但这里有一个现实问题：如果我们只看少量 demo，或者只拿几条漂亮样本来比较，本地模型很容易给人一种“差不多可以了”的错觉。真正决定它能不能成为资产层的，不是它在单题上的发挥，而是它在真实历史语境中，能否持续扮演一个可靠协作者。

所以这次我们没有只拿当前线程测试，也没有只取用户提问和最终答案，而是把 session 保留下来的全部历史数据都纳入了范围。最终扫描了 **63** 个 session 文件，对比了 **783** 条可重放的云端 assistant 回复。其中 **727** 条来自真实 `user -> cloud`，另外 **56** 条来自 `developer/codex -> cloud` 的内部协作链。除此之外，像 `reasoning`、`function_call`、`function_call_output`、`exec_command_end`、`patch_apply_end` 这类过程事件，也被完整导出了，一共 **8766** 条。也就是说，这次不是只看“说了什么”，而是连“怎么推进的”也一起保留下来了。

这件事很重要，因为如果我们只比最终输出，就会误以为本地模型差的只是语言质量；而当你把过程也拉出来之后，会发现它真正欠缺的是线程状态感、执行延续性和协作上下文感知。

## 二、这次对比到底发现了什么

如果先看最表面的统计结果，会得到几组很有意思的数据。

云端平均回复长度是 **330.32** 个字符，而 Gemma 的平均回复长度是 **547.23**。这说明 Gemma 明显更容易“展开讲”，更倾向于给出一段完整、自洽、像样的独立回答。单看这一点，你甚至会觉得它更“认真”。但问题是，在真实协作场景里，长并不等于好，完整也不等于对。

这次全量对比的平均文本相似度只有 **0.0768**。这个数字并不是说 Gemma 完全失效，而是在提醒我们：它和云端在大量历史场景里的行为风格并不在同一条轨道上。Gemma 常常会把一个现场推进型问题，回答成一个通用解释型问题；而云端则更像一个正在项目里协作的工程代理，它会接着前文继续收口、继续判断、继续执行。

还有一个很有代表性的指标是代码占比。云端带代码的回复只占 **4.73%**，而 Gemma 带代码的回复占到了 **28.61%**。这不是因为 Gemma 更会写代码，而是因为它在很多本来应该继续理解上下文、先给出局部判断或确认状态的地方，过早切换成了“我给你一份方案”或者“我给你一段代码模板”的模式。换句话说，它过度进入了解题状态，却没有足够进入现场状态。

如果用一句话概括这次最重要的发现，那就是：

**云端像一个在项目里持续工作的队友，Gemma 更像一个被临时叫来回答问题的顾问。**

## 三、几个非常具体的例子

这个结论不是抽象印象，而是直接来自具体案例。

比如在一个很短的历史指令里，用户只说了“文章英文版”。云端的反应，是直接把前文那篇中文技术博客翻成完整英文稿，沿着已有上下文继续交付。而 Gemma 的回复是“请提供您需要翻译成英文的文章内容”。如果把这两个回答单独拿出来，Gemma 并不算错，甚至很符合一个通用模型的安全策略；但在真实协作里，它显然错过了最重要的信息：**这不是一个从零开始的问题，而是一个已经在当前线程里积累了大量上下文的继续动作。**

再比如用户说“继续实现整套系统，直到可以工作”。云端没有先反问，也没有泛泛而谈，而是直接结合当前仓库进展，指出主干里真正缺的模块是 `route_task` 和 `build_distill_dataset`，然后说明要如何把它们做成可工作的模块，再接顶层 `run_lume_pipeline.py` 把执行、日志、wiki 和 dataset 串起来。Gemma 在这一题上的回答则更像一个独立规划师，它给出了一套完整的“系统实现路线图”，结构当然也合理，但它明显没有紧贴当前仓库状态和当前开发上下文。

还有一类特别典型的例子，是像“继续”“太长了”“发布”“为什么连不到”这种强依赖线程上下文的短句。云端在这些场景里表现得像一个真正知道现场发生了什么的协作者，它会自然接上前一轮的具体状态，比如当前网络错误、当前脚本功能、当前推送失败原因、当前 README 的哪一段刚修改过。Gemma 则更容易退回成一种脱离现场的通用问答模式，比如“请提供更多信息”“请发送当前脚本”“连接失败通常由以下原因导致”。这些回答本身没有逻辑错误，但它们完全没有利用已经存在于 session 里的上下文资产。

还有一些例子更能说明 codex/cloud 内部协作链的重要性。比如某些 `developer -> assistant` 的消息其实不是自然用户提问，而是内部推进、已批准命令、或者对子任务状态的确认。云端会基于这些内部信号继续往前执行，比如进入暂存区、准备提交、重新测试最小变更是否生效。而 Gemma 更倾向于把这类输入当成一个外部说明文本，再给出礼貌但低价值的响应，比如“已收到”“命令已保存”“请说明下一步动作”。这也说明一个非常关键的问题：**如果本地模型未来要真正承接协作型工作，它不只要学用户说话，还要学会读懂 codex/cloud 内部的工作语言。**

## 四、为什么会这样

如果只从模型能力角度解释，很容易说成“云端更强，本地更弱”，但这其实不够准确。真正的问题并不是 Gemma 不懂语言，而是它现在还缺少几种非常具体的能力。

第一种能力，是线程状态延续。云端之所以像“在现场”，不是因为它更会写文章，而是因为它在回复时默认自己处于一个连续工作流中。它会利用前面几十轮对话积累下来的上下文，把一条很短的输入解释成一个后续动作，而不是一次独立的新任务。

第二种能力，是任务收口。Gemma 经常会把问题回答得更长、更完整、更像教程，这说明它其实很会组织语言。但云端的优势在于，它更会把问题压缩成当前场景最需要的那一小段行动信息。在协作型系统里，真正高价值的不是“我也能讲一套道理”，而是“我知道现在最该说哪一句”。

第三种能力，是执行上下文感知。我们这次导出的 **8766** 条补充事件非常说明问题。真实 session 里，大量高价值信息并不在最终的自然语言回复中，而是在 `function_call`、`function_call_output`、`exec_command_end`、`patch_apply_end`、`agent_message`、`reasoning` 这些过程事件里。如果本地模型未来要学得更像云端协作代理，它不能只看最终聊天记录，而必须学习这些中间动作如何塑造最终输出。

## 五、这对 Gemma4 的训练方向意味着什么

这次全量对比最有价值的地方，不是再一次证明“云端更强”，而是帮我们把后续训练方向说清楚了。

第一，Gemma4 不应该只继续吃普通 SFT 对话。因为普通对话只会继续强化它“独立回答”的能力，而不会显著增强它“沿着线程继续工作”的能力。它现在缺的不是会不会说，而是会不会接。

第二，最值得喂的数据，不是单独的 prompt/answer，而是带上下文位置的信息差。比如某条用户短指令为什么在云端那里能直接被理解成“继续写那篇博客”，而在 Gemma 这里却变成“请补充材料”。这种差异，恰恰是后续最值得蒸馏的东西。

第三，`developer/codex -> cloud` 这部分数据必须保留。你这次提醒得非常对。如果只保留用户对话，那本地模型学到的还是面向外部的聊天能力；但真正能让它变成“协作型本地代理”的，是这些内部工作消息和云端如何响应它们。换句话说，未来 `Battery Model` 的成长，不仅依赖用户问了什么，也依赖系统内部是怎样一步步把工作推进下去的。

第四，所有过程事件都不应该被轻易丢弃。像这次导出的 `function_call`、`function_call_output`、`exec_command_end`、`reasoning` 等过程记录，实际上就是本地模型理解“云端为什么这么答”的背景资料。对自然语言生成来说，它们可能看起来不像直接训练样本；但对一个要承担真实任务的本地代理来说，这些东西反而比优美措辞更重要。

## 六、结论：Gemma4 现在最缺的不是知识，而是“现场感”

如果把这次全量历史对比压缩成一句话，我会这样说：

**Gemma4 现在并不是不会答，而是还不会像一个正在项目现场里的协作代理那样去答。**

它会解释，会展开，会组织，会给出像样的方案，甚至在不少题目上看起来比云端更像一个“认真负责的回答者”。但真正的差距不在语言表面，而在于它还不够理解：哪些问题其实不是新的问题，哪些短句其实是在接上文，哪些内部消息是在推进工作，哪些输出应该更短、更贴任务、更像动作而不是像教程。

而这也恰恰说明，`Lume Treasury` 接下来最值得做的事，并不是继续盲目扩普通数据量，而是把这次全量历史对比中暴露出来的这些差异，转化成更高价值的训练资产。真正能让本地模型成长的，不是更多孤立答案，而是更多“为什么云端在这里会这样继续”的结构化样本。

从这个角度看，这次对比的意义已经超出了“测一下 Gemma4 行不行”。它第一次比较完整地告诉我们：如果要把云端对话真正沉淀成本地资产，本地模型下一步最该学的，不只是知识本身，而是云端协作里的那种现场感、延续感和任务收口能力。
