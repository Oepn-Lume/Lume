# 为“现场”而生：从“图书馆研究员”到“常驻队友”，如何重构本地 AI 的工程实践

在大模型快速迭代的这两年里，行业似乎越来越相信一条简单公式：参数越大，模型越强；上下文越长，能力越完整；架构越复杂，系统越接近“通用智能”。但如果把观察点真正落在工程实践，而不是基准分数，我们会发现另一件更重要的事：本地模型最致命的短板，往往不是“知道得不够多”，而是“身处现场时反应不对”。

这正是 `Lume Treasury` 最近一轮全量对比里最鲜明的结论。我们把保留下来的历史 session 全部重放，让本地 `Gemma 4` 去回应那些云端已经真实回应过的任务。最后暴露出来的，不是传统意义上的知识欠缺，而是另一种更工程化的缺失：它缺少“现场感”，也缺少围绕现场状态持续工作的能力。

如果说云端模型像一个“在施工现场搬砖的资深工头”，能根据项目进度、文件状态、命令执行结果和上下文历史直接推动下一步；那么当前的 Gemma 更像一个“在图书馆查资料的实习生”。它当然知道很多，也能组织出看起来很完整的回答，但这些回答常常是脱离现场的，是理论化的，是“我可以讲明白”，而不是“我知道接下来该做什么”。

我们在 `Lume` 的全量对比中看到，Gemma 面对“继续”“发布”“为什么”这类强依赖上下文的短指令时，往往给出“通用解释”，而不是“现场动作”。平均文本相似度只有 `0.0768`。这不是知识问题，而是情境理解与状态延续上的系统性缺陷。

## 一、问题诊断：为什么“参数”不是答案

很多本地模型优化工作，默认仍然在沿着一个旧思路推进：继续扩数据、继续堆参数、继续追求更像一个大而全的顾问。这个方向不能说完全错，但它在工程场景里很容易失焦。

因为工程任务并不主要考验模型“能否给出一篇完整答案”，而更考验模型“能否根据当前状态给出下一个正确动作”。一个模型即使知识广博、措辞完整，如果每次都需要重新解释问题、重新询问上下文、重新整理现场，那它在真实工作流里仍然是不合格的。

这也是为什么 `Gemma 4` 目前的主要问题不能靠“再加一点参数”直接解决。它不缺百科式知识，它缺的是一种更贴工程的能力：理解自己现在站在哪里、前面发生了什么、接下来应该沿着哪条线继续。

## 二、五个最值得落地的改造方向

### 1. 训练数据从“问答对”升级为“状态轨迹”

传统 SFT 数据大多是平面的，去上下文的。`User -> Assistant` 两列一拼，就拿去训练。这种数据非常适合让模型学会“答得像样”，但不适合让模型学会“接得住现场”。

如果用户说“继续”，模型的输入不能只剩一个“继续”。它至少应该同时看到前几轮对话、最近一次 patch 成功事件、当前文件状态、最近命令结果。只有这样，它才知道这不是一个新的问题，而是前一个操作链上的延续。

在 `Lume Treasury` 里，这已经不只是理论建议。我们已经把全量 session 对比构造成了新的 `on-site alignment` 数据集，生成了：

- `onsite_alignment_sft.jsonl`
- `developer_chain_sft.jsonl`
- `onsite_alignment_dpo.jsonl`

这些数据不再只是普通问答，而是显式带有：

- `Session_History`
- `Internal_Events`
- `Current_State`
- 当前短指令

这意味着后续训练不再只是教模型“怎么说”，而是在教它“如何站在现场继续往下做”。

### 2. 用“负向对比”训练模型学会收口

从 `gemma_vs_cloud_all_sessions.json` 里，我们已经看到了大量非常典型的失败样本：云端已经顺着上下文直接行动了，而 Gemma 还在请求补充信息；云端只回一句贴任务的指令，Gemma 却展开一整段教程；云端知道现在该动什么文件，Gemma 还在泛化讨论“通常可以这样做”。

这类数据的价值极高，因为它不是抽象意义上的“标准答案”，而是本地模型和更优现场答案之间的真实差距。我们已经把这类差距直接写进 `onsite_alignment_dpo.jsonl`，用来支持后续的偏好对齐。

这里最重要的一个训练原则是：**严厉惩罚在上下文已经存在时，模型仍然向用户索取冗余信息。**  
像“请提供文章内容”“请告诉我你要继续什么”“请发一下脚本”这类行为，在聊天模型里看似礼貌，但在工程现场里往往意味着它已经脱线了。

### 3. 架构层要显式注入“现场状态”

很多时候，不是模型完全没看到上下文，而是本地推理时对长上下文的利用会快速衰减。它看到了信息，但没真正把这些状态组织起来。

所以在 `Lume` 里，我们开始做一件很直接的事：不只传聊天历史，而是在本地规划前动态注入 `<field_report>`。

这个 `field_report` 里会包含：

- 当前推测工作目录
- 最近一次命令结果
- 最近待完成任务
- 当前关注点
- 最近 reasoning 摘要
- 最近 patch 事件
- 最近文件路径

这不是为了让 prompt 更花哨，而是为了强行给模型戴上“现场 VR 眼镜”。它需要被提醒：现在不是在闲聊，而是在一个有状态、有上下文、有任务连续性的工程环境里继续工作。

与此同时，我们还实现了“短指令扩展”。当用户输入少于 5 个词，例如“继续”“发一下”“下一步”，系统会自动补上最近任务摘要、最近文件、最近命令结果，再一起送入本地模型。这一步的目标非常明确：把短指令从“语义模糊”改造成“状态唤醒”。

### 4. 内部协作链要单独对齐

`developer/codex -> cloud` 这一类消息，不能再被当成普通聊天。它本质上更接近一种内部协议，或者行动级信号。

如果模型看到的是类似“已批准”“继续”“按这个提交”“只推送这一批文件”这样的内部指令，它的最佳响应应该是：

- 极短
- 极明确
- 能推进状态

而不是展开解释。

在这次数据构建里，我们已经把这类样本单独切成了 `developer_chain_sft.jsonl`。这一层的目的，就是训练本地模型学会区分：什么时候自己是在面向用户解释，什么时候自己是在面向内部协作链执行。

### 5. 评估要从“像不像”转成“能不能收口”

相似度 `0.0768` 这件事本身已经说明，传统文本相似度指标在工程场景里非常有限。你很难要求本地模型在文字上复刻云端，但你可以要求它在动作上对齐云端。

更合理的评估指标应该是：

- 是否触发了正确的函数调用
- 是否沿用了正确的参数结构
- 回复长度是否逼近云端的收口尺度
- 是否引用了当前 session 中的重要文件名、变量名和函数名
- 面对“继续”这类指令时，是否真的沿着上一条状态继续

换句话说，工程里的好模型，不是“更会说”，而是“更会收口”。

## 三、最关键的范式变化：从“临时顾问”到“常驻队友”

这轮分析里，最关键的观点并不是“Gemma 还不够强”，而是：**我们一直在用错误的角色期待它。**

如果你把它当成一个临时顾问，那么它现在已经不差了。它会解释，会总结，会给结构化方案，会写出看起来像样的回答。

但如果你把它当成一个真正的本地工程队友，那么标准就完全变了。一个常驻队友必须知道：

- 前面执行了什么
- 哪些文件已经改过
- 哪些命令成功或失败
- 当前服务是否在运行
- 这串操作的最终目标是什么

我们把这种能力叫做“读档”。它不是记忆某一段聊天，而是理解整个工作会话的状态存档。

也正因为如此，`Lume Treasury` 现在最正确的方向，不是让 Gemma 变得更像一个更强的聊天模型，而是让它变得更像一个懂得读档、懂得续接、懂得现场收口的常驻队友。

## 四、下一步最具体、最值得做的事

如果说有一件事值得立刻推进，那就是把那 **8766 条过程事件** 真正变成模型可以利用的“中间状态链”。

这些事件并不是噪声，相反，它们才是云端那句短而准回复背后的真正依据。用户之所以只说一句“继续”，云端却知道怎么接，是因为在它的工作上下文里，已经隐含了分支状态、最近 patch、最近测试结果、最近命令输出和操作轨迹。

如果我们能把这些状态链条重新组织成训练输入，例如：

- 用户创建了新分支 `feature/auth`
- 修改了 `user_controller.py`
- 单元测试通过
- 提交到暂存区
- 用户说“继续”

然后把目标输出定义成：

`运行集成测试并部署到 staging 环境`

那本地模型学到的，就不再是“继续”这个词的百科解释，而是“在这种上下文里，继续意味着什么”。

这才是本地 Battery Model 真正应该积累的资产。

## 五、结语：本地 AI 的真正价值，是在特定上下文里做出正确的下一个动作

很多时候，我们过于强调模型的知识宽度，却忽视了工程场景里更重要的一件事：在一个具体的、连续的、会变化的状态空间里，模型能不能做出正确的下一个动作。

这篇方案想推动的，不是让 AI 再多懂一些常识，而是让它少忘一些现场。记住会话状态，记住操作历史，记住项目上下文，记住用户现在真正身处哪条工作链上。

只有做到这一点，本地模型才会从一次性的问答工具，逐渐变成一个真正的常驻队友。它不需要先变成全能的百科全书，它需要先变成一个可靠的现场参与者。

这也是工程化 AI 最真实的价值所在：不是在 benchmark 上高出几个百分点，而是在开发者说出“继续”的那一刻，真正知道从哪里继续、继续什么、又该如何继续。
